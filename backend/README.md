# China Quest backend contract (local prototype)

`schema.sql` is an executable **development schema**, not a formal Supabase migration. It is validated only in a fresh local PGlite PostgreSQL database. No cloud project, account, pairing flow, RPC transport, or bidirectional sync is configured by this directory. The Android app remains local first; its outbox must not be uploaded until a trusted family/child pairing flow, authenticated transport and operational migration are implemented.

Run `npm ci --ignore-scripts` and `npm test` from this directory with Node 24. The tests create an in-memory PostgreSQL instance, install a test-only `auth.uid()` shim and test roles, apply `schema.sql`, then exercise RLS using `SET ROLE authenticated`. The shim is never part of the deployment schema. The exact PGlite version is pinned in `package-lock.json`.

The trusted server creates `families`, `parents`, `children`, `child_accounts` and `device_child_links`. A parent's database user ID is paired to one family; a child user ID is paired to one child. Email is not required for a child. No client can create or change these mappings. The server also computes mastery, sessions, review and quiz projections, and reward outcomes. `family_reward_budgets` is visible and configurable only to a family parent. Clients may submit typed append-only `sync_events`; the database derives evidence source from the event kind. Replaying the same UUID and same fields returns `duplicate`; changing any field for that UUID raises `SYNC_EVENT_CONFLICT`.

`fromAndroidEnvelope` maps the current Android SQLite outbox to the typed RPC contract using a **trusted** local-child-to-server-child pairing. It rejects `CHILD_SETTINGS` (there is no parent settings transport), PARENT evidence claims and mismatched task/source/skill combinations. It ignores any client identity claim: Postgres obtains `actor_user_id` from `auth.uid()`. Local event IDs remain the stable sync IDs. A future transport must pass only `toIngestArgs(...)` to the RPC under the signed-in user's access token and handle `accepted`, `duplicate` and conflict separately. Never put a service key in Android.

Only content with `approved_version_hash = content_hash` is visible to a child. Source name, version and URL remain explicit. A trusted editor must reapprove each changed content hash; a prior approval cannot silently carry over.

For deployment, create an actual migration with the Supabase CLI after pairing and operational review. Check the project Data API exposure settings, grants, RLS policies and advisors against the deployed Supabase version. The local executable schema intentionally creates no remote resources. See [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [API access controls](https://supabase.com/docs/guides/api/securing-your-api).
