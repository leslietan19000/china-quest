# China Quest engineering rules

This is a long-term supervised family learning system. Preserve the user's full product principles in PRODUCT_SPEC.md and the domain specs. Work in ordered phases and never block the first offline APK for AI, Creator or Builder features.

- Child learning must work with no network or AI. Never erase mastery when a season changes.
- No sibling rankings, punitive streaks, ads, feeds, automatic purchases or public child publishing.
- Core facts must be sourced. Teaching drafts marked NEEDS_REVIEW stay off child screens.
- Scope all child rows and events; use transactions and stable event IDs. Protect parent authority server-side, never with user-editable metadata.
- No service secrets in code, APKs or browser bundles. No real child data in fixtures.
- No production deployment, paid resources, account changes or real child cloud uploads without user authorization.
- Child coding changes are sandbox/branch proposals with exact-version parent approval. No secrets, dependency changes or production deploy capability for child prototypes.
- Run appropriate build/tests once; repair based on evidence. At most two materially identical failures. Stop that dependency branch until a condition changes. No polling loops or AI calls to wait for resources.
- On a high-capability model, delegate mechanical/exploratory work to cheaper agents when practical; normal implementation to mid-tier. Do not duplicate expensive work.
- Update PROGRESS.md each phase: completed, actual tests, known issues and next phase. APK compilation is not BOOX hardware acceptance.
- Keep toolchains and generated artifacts out of Git; preserve the local debug keystore for pilot upgrades.

Commands: `tools/android-build.ps1`, `python tools/content-validate.py`. See docs/ENVIRONMENT.md for local Windows Java IPC compatibility and docs/QA_PHASE_1.md for evidence.
